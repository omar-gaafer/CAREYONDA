# Model B — Independent Validation Protocol

Status: protocol specification only; a research-only benign exercise control is now defined, but no datasets were generated, no models were trained, and no threshold was selected.  
Scope: synthetic Model B evaluation. This protocol does not establish clinical validity or operational suitability.

## 1. Availability decision

**Independent validation is not possible with the data currently available.** The canonical seed-42 dataset has 32 episodes, but the full dataset and its feature/scenario patterns were inspected in Part 1. The `windows_handoff_verification` and `mvp_demo_20261114` copies have the same feature and label hashes as the seed-42 snapshot. They are copies, not new episodes. The user-identified 780-sample evaluation was inspected previously, and its episode membership is not recorded in the repository. It must not be used for additional model or threshold selection.

Although the existing rows can be mechanically repartitioned by episode, no partition can now be certified as unseen for validation or final testing. Do not relabel a random subset as independent. The seed-42 data and the earlier 780-sample result are **historical development material only** for a new confirmatory experiment.

No validation/test data is generated by this document. Fresh data must be created and reserved after the protocol, label semantics, sample-size plan, and alert budgets are frozen.

## 2. Episode split specification

Use distinct, purpose-specific simulator runs. A whole run belongs to exactly one role; no episode or observation may occur in more than one role. Each run contains five scenarios: `baseline`, `elevated_co2`, `sleep_deprivation`, `recent_exercise`, and the research-only `benign_exercise_control`.

| Role | Proposed simulator seed | Episodes per scenario | Total episodes | Permitted use |
| --- | ---: | ---: | ---: | --- |
| Training | 4201 | 100 | 500 | Fit preprocessing and challenger models. Only `baseline` episodes enter unsupervised fitting. Other scenarios, including controls, are excluded from fitting. |
| Validation | 4202 | 30 | 150 | Select model/threshold and report development metrics. Includes 30 episodes of each scenario, including benign exercise controls. |
| Final test | 4203 | 30 | 150 | One final evaluation after model, features, preprocessing, labels, and threshold are frozen. No development decisions may use its results. |
| Historical development | Existing seed 42 and prior 780-sample result | — | — | No role in the new confirmatory split; do not use for threshold selection or final metrics. |

The seed values and counts above define the user's requested deterministic plan; they are not generated datasets. The four core scenarios use `SimulationConfig.episodes_per_scenario`; the extension must use the same count for `BenignExerciseControlConfig.episode_count`. Do not infer sufficiency from row counts: each episode contributes repeated, temporally overlapping samples. The requested counts are not a claim of adequate statistical power or confidence-interval precision.

The simulator seed determines each run. Assign all episodes and observations in that run to its one role. Keep the control generator's derived seed in the manifest. The extension checks control IDs against the four core scenarios within the same run, but independently generated runs have no shared ID registry. Therefore, before fitting, compare the exact episode, sample, observation, and evidence ID sets across all three run manifests; fail closed and do not evaluate if any IDs overlap. Also verify scenario counts, label joins, and expected observation counts. Persist these manifests. Do not repartition the previously inspected data to simulate independence.

Keep final-test files and labels unavailable to the model/challenger developers until the validation-selected procedure is frozen. Store their hashes in a restricted manifest before evaluation; disclose the manifest and seed after the final run. These are synthetic samples from the same generator, so a separate seed estimates variation under the same synthetic assumptions only. It does not provide independent real-world or clinical validation.

## 3. Feature and preprocessing rules

Use the versioned 16 predictors and exact order in `datasets/synthetic/m1_2_seed42/feature_schema.json`. Exclude `sample_id`, `episode_id`, mission/astronaut identifiers, scenario labels, expected-label proxies, run/seed metadata, evidence IDs, timestamps, and provenance from the predictor matrix. Keep them in a separate evaluator-owned metadata table for grouping and metrics. The research extension returns `ResearchLabel` values in a separate mapping keyed by `sample_id`; its scenario names and `expected_anomaly_proxy` must never be merged into `FeatureSample.values` or passed to a challenger.

The current features are event-time, retrospective 5-minute window summaries. Keep every row from one episode together. The simulator can assign ingestion delays; this dataset is not an arrival-time replay. Do not present offline event-time evaluation as live/online performance.

For each fitted candidate:

1. Use training episodes only to fit the imputer and any other transformer. In the unsupervised fit, use only `baseline` training episodes.
2. Apply those frozen training transforms to validation and final-test matrices. Never recompute medians, scales, feature selection, encodings, or missingness rules from validation/test data.
3. Keep schema `*_missing` predictors. Preserve the original null mask separately, never replace missing values with zero, and report coverage and null counts per feature and split. If an input column is entirely missing in training, fail with an explicit unsupported-feature result; do not infer a fill value from validation.
4. Use the declared fatigue encoding (rested=0, tired=1, very_tired=2) and boolean encoding (false=0, true=1) consistently. These are synthetic encodings, not calibrated ordinal distances.
5. Record the fitted imputation values and feature order in the experiment manifest. A candidate may not silently reorder, drop, or add columns.

The currently checked-out `m1_2_seed42/features.csv` has a leading blank line and does not parse with the expected `sample_id` header. It is not a valid input until repaired through a separately authorized data-integrity task. Do not repair or overwrite it in this protocol task. A clean duplicate has the expected hash but is still the same inspected seed-42 dataset.

## 4. Common challenger interface

The evaluation harness owns split metadata, thresholds, and metrics. Candidate adapters own their fitted preprocessing, but must learn it from training rows only and expose its parameters. Candidates receive only ordered predictor matrices; they do not receive scenario labels, split names, episode IDs, or evaluation truth.

```python
class FittedScorer(Protocol):
    def score(self, X: FeatureMatrix) -> Sequence[float]: ...


class Challenger(Protocol):
    def fit(
        self,
        X_train: FeatureMatrix,
        *,
        feature_names: tuple[str, ...],
        random_state: int,
    ) -> FittedScorer: ...
```

Contract requirements:

- `FeatureMatrix` is an `N × 16` row-major numeric matrix in the schema’s exact column order; NaN represents an unavailable feature value, and the original missing mask is retained by the harness.
- `fit()` receives only training baseline rows and returns a fitted scorer. Any candidate-specific fitted preprocessing must be learned inside this call from those rows only and exposed in the run manifest. Use the same preprocessing policy across candidates unless a predeclared model requirement justifies a difference.
- `score()` returns exactly one finite scalar per input row, in input order. **Higher scores always mean more anomalous.** Invalid shape, non-finite scores, or ID/order mismatch fails the run.
- The harness applies the same externally selected threshold rule to every candidate: `flag = score >= threshold`. Do not compare candidate-specific `predict()` flags that use different built-in contamination thresholds. For the existing Isolation Forest, adapt its score as `-score_samples`; its built-in `predict()` is not used for common-threshold evaluation.
- Evaluation metadata is joined by `sample_id` outside the model interface. Duplicate/missing IDs or metadata joins fail closed.

## 5. Threshold selection specification

Threshold selection occurs **only on validation data**, after all features, candidates, labels, and constraints have been fixed. For each candidate, evaluate thresholds between consecutive unique validation scores (including all-positive/all-negative boundary choices). Flag a sample when its score is greater than or equal to the chosen threshold.

Before validation is opened, the research owner must specify two numeric alert budgets:

- `B_max`: maximum sample-level false-positive rate among validation baseline episodes.
- `E_max`: maximum alert rate among **labeled benign-exercise control samples** where `exercise_active_latest == 1`.

Do not invent or infer these budgets from the current data. They are research operating constraints requiring explicit review; they are not clinical thresholds.

Among thresholds satisfying both budgets, select the one maximizing the unweighted macro-average of sample-level recall across `elevated_co2`, `recent_exercise`, and `sleep_deprivation`. Break ties by lower baseline false-positive rate, then lower benign-exercise alert rate, then the higher threshold. If no threshold is feasible, record “no feasible threshold”; do not relax constraints after seeing results.

**Exercise-label treatment:** `recent_exercise` remains a positive synthetic proxy scenario. The separate research-only `benign_exercise_control` has expected proxy label negative, so its active-exercise samples define the `E_max` alert-rate denominator. Report the `recent_exercise` exercise alert rate descriptively and through scenario-specific recall; do not count it as a false positive. This resolves the missing-control label definition, but threshold selection remains blocked until numeric `B_max` and `E_max` values are approved.

After selection, freeze the model, preprocessing, feature order, scenario-to-evaluation mapping, `B_max`, `E_max`, and threshold. Apply that single threshold once to final-test data. A failed test constraint is reported as a failed result; do not retune on test data.

### Threshold stability

On validation only, perform 1,000 stratified episode-cluster bootstrap resamples using fixed bootstrap seed `4243`. Resample whole episodes within scenario, re-run the same feasible-threshold selection rule, and record the threshold distribution and whether each resample has any feasible threshold. Report the median, interquartile range, 2.5th/97.5th percentiles, and feasible-resample fraction. Also report the fraction of bootstrap thresholds that pass each constraint. This measures sensitivity to the available validation episodes; it does not make a small validation set independent or representative. Threshold stability is summarized within each candidate/model seed; absolute score thresholds are not comparable across different model families.

Use the same predeclared model random state `42` for the primary comparison. If stochastic-seed sensitivity is studied, predeclare a common seed list (for example 42–46) and report all runs; do not select the best random seed by validation performance.

## 6. Metric definitions

Use the frozen binary evaluation convention only for synthetic proxy analysis:

| Scenario | Expected proxy label | Evaluation treatment |
| --- | ---: | --- |
| `baseline` | 0 / negative | Baseline false-positive constraint (`B_max`). |
| `benign_exercise_control` | 0 / negative | Benign-exercise alert constraint (`E_max`), calculated only over samples with `exercise_active_latest == 1.0`. |
| `elevated_co2` | 1 / positive | Scenario-specific recall. |
| `recent_exercise` | 1 / positive | Scenario-specific recall; its active-exercise alert rate is descriptive and is not counted against `E_max`. |
| `sleep_deprivation` | 1 / positive | Scenario-specific recall. |

State this mapping in every report; these synthetic proxy labels are not clinical anomaly ground truth. Labels are attached to sample IDs in evaluator metadata, never inferred from model inputs.

**Synthetic shortcut risk:** the current control generator uses a fixed default heart-rate response fraction of `0.5`, while `recent_exercise` uses the full configured response. The exercise-active indicator is shared, but this hand-set heart-rate amplitude creates a direct, potentially strong scenario cue. A model may learn the simulator's label construction rather than a robust distinction between benign exertion and health anomalies. Report this limitation and predeclare ablations of heart-rate features and exercise-context features before interpreting results. Treat performance as simulator-specific; do not claim physiologic or operational validity. Do not alter this assumption after inspecting validation or final-test outcomes.

| Metric | Definition |
| --- | --- |
| Precision | `TP / (TP + FP)` at the frozen threshold. If no rows are flagged, report undefined with its denominator; do not hide the case with an implicit zero. |
| Recall | `TP / (TP + FN)` at the frozen threshold. |
| F1 | Harmonic mean of precision and recall at the frozen threshold. |
| PR-AUC | Average precision from continuous anomaly scores and binary proxy labels; report the implementation/convention and positive prevalence. |
| Scenario-specific recall | Recall calculated separately for each positive scenario, including `recent_exercise`; do not report only a pooled value. |
| Baseline false-positive rate | Baseline rows flagged / all baseline rows. Also report baseline episodes with ≥1 flag / baseline episodes. |
| Exercise flag rate | Among samples with `exercise_active_latest == 1.0`, the fraction flagged by the model. Report separately for benign exercise controls and the synthetic `recent_exercise` scenario; only the former can count against `E_max`, while `recent_exercise` contributes to positive recall. |
| Episode-level detection | For each positive scenario, episodes with ≥1 flagged sample / positive episodes. Also report per-episode fraction of samples flagged and the baseline episode false-alert rate. |
| Threshold stability | Validation episode-bootstrap threshold median, IQR, 95% percentile interval, feasible-resample fraction, and constraint-pass fractions. |

Report sample and episode denominators beside every rate. Do not treat the 30 time samples within an episode as 30 independent experimental units.

## 7. Uncertainty and reporting

Report counts by split and all five scenarios; episode counts, unique episode IDs, and samples per episode; feature null counts and coverage; positive prevalence; selected threshold and constraints; and all model/data versions. A result without its episode IDs, hashes, and split manifest is not reproducible.

For metric confidence intervals, use a stratified cluster bootstrap that resamples whole episodes within scenario, not individual rows. Use 1,000 replicates and recorded bootstrap seed `4243`; report 95% percentile intervals and denominators. For per-scenario rates, resample episodes within that scenario. If an interval is unstable or an episode count is too small, report the counts and interval as inconclusive rather than relying on row-level precision. PR-AUC intervals must also use episode-cluster resampling.

Threshold uncertainty comes from the validation bootstrap described above. Final-test confidence intervals are computed after the threshold is frozen; they do not feed back into model choice. With only synthetic data, all intervals describe generator variability, not uncertainty about real astronaut health or mission risk.

8. There are no verified baseline model/report artifacts. The current four-fold evaluation and `contamination="auto"` do not implement this validation-only threshold protocol.
